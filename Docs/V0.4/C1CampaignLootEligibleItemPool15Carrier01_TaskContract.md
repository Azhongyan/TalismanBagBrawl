Create the first Item-owned technical prerequisite for the accepted
`V0.4-C1CampaignLootPool15PlayableProof01` experiment:

- expose exactly fifteen ordinary low-rarity Campaign Item identities through
  one immutable canonical pool;

roster, mount Cards, or produce the playable five-clear loop.

## 10. Immutable Pool/Profile Contract

Use local immutable conventions under namespace
`TalismanBag.Items.CampaignLoot`.

The public pool snapshot must expose at minimum:

- schema ID, carrier version, algorithm ID, product context and pool ID;
- exactly fifteen defensive-copied Item profile rows in stable base-identity
  order;
- exactly five defensive-copied effect-family descriptors;
- exactly three rows per family;
- pool canonical signature and source Item catalog canonical signature;
- immutable Reward, Battle and presentation dependency inventories.

Each Item profile must expose at minimum:

- base Item ID and explicit `white` rarity/version identity;
- family ID and stable family variant ID;
- candidate semantic source identity/signature and maturity;
- normalized trigger ID, condition ID, operation ID, target-stat/scope ID and
  native unit identity from the current candidate lineage when available;
- explicit cue identity and presentation profile identity;
- shape/core/catalog lineage needed to reject stale identity;
- numeric payload maturity/status plus nullable numeric fields.

Numeric requirements:

- all non-I002 new combat magnitudes, cooldowns and first-trigger offsets are
  absent and marked `CANDIDATE_PENDING_BALANCE` or an exact equivalent;
- current released I002 baseline may be referenced as authoritative lineage,
  but this package must not copy or broaden the starter baseline implementation;
- candidate Workbench values may be exposed only as source lineage metadata,
  never as a formally executable value;
- absence is not represented by zero.

The complete profile and pool canonicalization must be unambiguous,
invariant-culture, order-stable and lowercase SHA-256.

## 11. Deterministic Instance And Entitlement Carrier

The Item carrier accepts a Reward-resolved identity; it does not perform RNG.

Accepted request facts must include:

- exact product context and pool ID;
- non-empty authoritative reward grant/claim identity supplied by Reward;
- selected base Item ID and `baseItemId@white` version identity;
- selected Item profile canonical signature;
- pool canonical signature and Item catalog canonical signature.

Accepted result must expose:

- accepted/changed/diagnostic;
- normalized request lineage;
- stable `itemInstanceId` derived from an unambiguous SHA-256 materialization
  payload that includes the reward grant identity and selected profile;
- immutable `instanceCanonicalSignature`;
- stable Item-owned entitlement identity/signature;
- defensive copy of the selected Item profile.

Required semantics:

1. The same request is byte-identical and idempotent.
2. A different reward grant identity produces a distinct instance even when
   the same base Item becomes eligible again after two intervening drops.
3. Unknown/non-pool Item, I001, I031, non-white rarity, stale pool/profile/
   catalog signature, empty grant identity or malformed input rejects with no
   partial snapshot.
4. No static mutable session, reward history, claim state or inventory roster
   is retained.
5. No `System.Random`, Unity RNG, QA Roll engine, probability, stage mapping or
   reward-choice logic is used.
6. Affixes, rarity economy, Build/Core, placement, lighting and live combat
   state are not invented.

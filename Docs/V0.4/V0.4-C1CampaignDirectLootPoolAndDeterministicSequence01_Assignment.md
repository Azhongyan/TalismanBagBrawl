### 9.2 Immutable session/reducer

Expose an immutable Reward session specification/snapshot and a pure
create/resolve API. The snapshot owns only:

- exact product context, chapter, run session ID and explicit `long rootSeed`;
- last two accepted base Item identities;

- next expected clear sequence, initial-progression/replay phase and a
  canonical signature.

No static mutable singleton, PlayerPrefs, Scene object, Inventory roster or
Save data is allowed.

### 9.3 StageClear eligibility and retry semantics

1. Accept only canonical-valid `CAMPAIGN_NORMAL_LV1`, non-Boss StageClear
   facts for exact chapter and stages 1-1..1-5.
2. First accepted clear in a session must be 1-1/sequence 1, followed by the
   exact initial stage/sequence order through 1-5/sequence 5.
3. The same byte-identical StageClear submitted again returns the original
   accepted grant and unchanged session snapshot.
4. After the initial fifth clear, a new canonical-valid StageClear with the
   next sequence and an eligible 1-1..1-5 stage is a new replay reward
   opportunity, even when that stage was previously rewarded. It produces a
   distinct grant/claim/dedupe lineage and continues recent-two history.
5. Reusing a prior StageClear ID with conflicting battle/result facts, or
   reusing a prior clear sequence for a different fact, rejects unchanged.
6. Out-of-order, stale, wrong-session/context/chapter/stage, Boss, malformed or
   canonical-mismatched facts reject without changing history.
7. A newly created explicit session may start a fresh experiment chain. This
   package makes no durable first-clear claim across app reloads.

### 9.4 Equal-weight deterministic selection

1. Candidate set is the fifteen released Item profiles minus the last two
   accepted base identities.
2. Every remaining base identity has equal weight; source collection order
   must not alter the selected result.
3. Derive selection only from the immutable session root seed, run session,
   accepted drop ordinal, correlated StageClear canonical, policy identity and
   pool canonical.
4. Use a documented deterministic SHA-256-based unbiased index selection; no
   `System.Random`, `UnityEngine.Random`, QA Roll engine or floating point.
5. The selected base Item may repeat only after two intervening accepted base
   identities.

### 9.5 Contract/result assembly

For each new accepted StageClear, whether first occurrence or replay:

1. Build one valid `DropRequest` with source `StageClear`, the frozen policy
   identities and one `OrdinaryRoll` slot. Mode is `FirstClearOnline` for the
   stage's first accepted occurrence and `RepeatChallengeOnline` thereafter.
2. Derive a non-circular authoritative reward grant identity from session,
   StageClear, request, selected profile and policy/pool canonicals.
3. Call only the released Item materializer. A rejected/null/stale Item result
   aborts the whole Reward resolution unchanged.
4. Build one valid `DropRollResult` using the Item-owned `itemInstanceId` and
   `instanceCanonicalSignature`.
5. Build one valid `RewardResult`/`RewardEntry` with the same Item identity and
   quantity `1`.
6. Build stable `RewardClaimIdentity` and `RewardDedupeIdentity`. Claim scope
   includes exact run-session + chapter + stage + clear sequence + acquisition
   mode. Dedupe is per unique accepted StageClear opportunity; it may not
   collapse a later legitimate replay clear into the first-clear claim.
7. Validate every contract using `RewardDropContractValidator` before the
   immutable session advances.
8. Return one immutable grant bundle containing the six Reward contracts plus
   the Item-owned materialization/entitlement snapshot. Do not convert that
   bundle into an Inventory write or claim that Item roster accepted it.

All failure paths are atomic: no partial history, claim, dedupe, selected Item
or next-stage advancement.

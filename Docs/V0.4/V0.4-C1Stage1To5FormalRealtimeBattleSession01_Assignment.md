## 5. Required Implementation

### 5.1 Encounter Admission

Support `CAMPAIGN_NORMAL_LV1` stages `1-1` through `1-5`.

For `1-1/1-2`:

- Preserve current accepted early encounter catalog validation.
- Preserve exact deterministic oracle parity where it currently applies.
- Preserve I001/I002 starter behavior and optional inactive I002 rules.

For `1-3/1-4/1-5`:

- Require exact balance profile
  `campaign.normal.lv1.balance.c1.stage3to5.playtest.v1`.
- Require exact encounter variants from the Enemy release.
- Require expected enemy canonical
  `79d5e5d0b3cb18f0e5a854dbba1327b1ad7948702ff3c581b0e67eebd948058c`.
- Resolve via `C1Stage3To5PlaytestEnemyEncounterCatalog`, not by copied
  constants or label inference.
- Reject wrong context, wrong balance profile, wrong variant, wrong canonical,
  invalid Enemy validation, stale generation, duplicate session, and reset
  mismatch.

### 5.2 Formal Item Input

- Continue to consume the existing formal Item battle snapshot.
- For `1-3/1-4/1-5`, accept the released Pool15 and five-family formal Item
  facts with `0`, `1`, or `2` active placed+lit rows.
- Do not require the old I001/I002 row-count translator for `1-3/1-5`.
- Do not fabricate active Item facts for unplaced or unlit rows.
- Existing paused live-refresh semantics remain valid: refresh only future
  Item actions, never restart the Session or rewrite past ledger history.

### 5.3 Actor State And Targeting

- Instantiate one Battle-owned runtime actor state per released Enemy actor row.
- Use released actor IDs, content IDs, runtime/operator IDs, occurrence order,
  max HP, action IDs, request keys, and canonical signatures.
- Battle owns current HP, death, current target, retargeting, and terminal
  conditions.
- Default target selection: first living actor in released roster order unless
  an existing Battle-owned targeting rule already gives a stricter deterministic
  result.
- Emit target/death/HP cue truth from accepted Battle state changes only.

### 5.4 Enemy Actions

- Schedule the released shared basic wave using the Enemy release values:
  first `4500ms`, interval `4500ms`, damage `7`, one application.
- Apply shared basic wave to player HP through the existing Battle-owned
  player damage pipeline.
- Bind Bone Swap as a Battle-owned operator using only `BoneSwapRelease`:
  accepted source kind, ratio, cap, telegraph, recovery, and pending policy.
- Bone Swap may only consume accepted current-generation single-target direct
  damage applications. Rejected, duplicate, stale, area, unsupported, or
  terminal-invalidated events must not feed it.
- `LATEST_WINS_ONE_SLOT` means one pending return slot per legal Bone Swap
  operator; newer legal source events replace the pending payload until resolve.
- Terminal, reset, unbind, target death, or illegal operator state must cancel
  or reject pending Bone Swap actions without stale playback.
- Actor actions marked `BATTLE_CONTRACT_REQUIRED` must remain explicit. If an
  action has no released Battle effect semantics, report it as unsupported or
  diagnostic-only; do not coerce it into basic damage, zero damage, or a fake
  working skill.

### 5.5 Results And Terminal

- Preserve current `BattleResultSnapshot` safety:
  `shouldWriteSave=false`, `shouldGrantReward=false`.
- `1-1/1-2` no-refresh paths retain existing oracle parity expectations.
- `1-3/1-4/1-5` terminal truth is the accepted live Session result. Do not
  require the old `C1Lv1FormalBattleApplication` oracle and do not precompute
  or replay-only a terminal summary.
- Session reset, unbind, duplicate launch, stale generation, stale reset,
  wrong canonical, wrong context, and terminal-after-refresh cases must remain
  idempotent and fail closed.

## 9. Required Behavior

1. Clean-start and completion-aware `CreateSession` overloads remain available;
   the clean overload supplies a valid empty completion proof.
2. Every accepted grant carries the exact accepted completion proof and session
   specification, plus an immutable defensive copy of the effective completion
   prefix immediately before that opportunity.
3. The pre-op prefix is the sole completion evidence used to prove mode:
   membership means `RepeatChallengeOnline`; the exact first missing stage means
   `FirstClearOnline`; a later gap rejects.
4. StageClear identity, canonical signature, session, sequence, stage and mode
   are correlation fields. Ordinal/sequence never determine completion truth.
5. Grant v2 canonical/signature covers the complete admission lineage and all
   existing grant units. Proof, spec, prefix, lineage, stage, mode or correlation
   tampering invalidates the grant and its containing session before mutation.
6. A byte-identical StageClear retry returns the original immutable grant and
   unchanged snapshot with no duplicate grant.
7. New sessions restore no opportunities, recent-2 history, RNG position,
   reward session or mid-battle state.
8. Reward remains sole owner of pool15/equal RNG/recent-2, acquisition mode,
   accepted opportunity, roll/result, claim/dedupe and materialization.
9. Mainline supplies only the completion proof inputs and StageClear facts; Item
   later validates and consumes the untouched Reward grant.
10. Unknown, malformed, stale, conflict, duplicate or tampered input fails closed
    with no partial state change.

## 10. Public Immutable API And Canonical Units

### Existing proof/session API retained

- `C1CampaignCompletionOnlyProgressProof.v1`
  - public fields: authority/context/chapter, immutable `CompletedStageIds`,
    `canonicalPayload`, `canonicalSignature`
  - factories/verification: `Create(...)`, public `IsCanonicalValid()`
  - canonical units: schema, authority, context, chapter, completed count, exact
    ordered completed-stage prefix
- `C1CampaignDirectLootSessionSpecification.v2`
  - public fields: context/chapter, runSessionId, rootSeed, completionProof,
    canonical payload/signature
  - verification: public `IsCanonicalValid()`
  - canonical units: schema, context, chapter, session, seed, proof signature
- Resolver overloads:
  - `CreateSession(string runSessionId, long rootSeed)`
  - `CreateSession(string runSessionId, long rootSeed,
    C1CampaignCompletionOnlyProgressProof completionProof)`

### New completion-aware grant API

- `C1CampaignDirectLootGrantAdmissionLineage.v1`
  - public fields: completionProof, sessionSpecification, immutable
    `PreOpportunityEffectiveCompletedStageIds`, runSessionId, stageClearId,
    stageClearCanonicalSignature, clearSequence, acceptedStageId,
    acceptedAcquisitionMode, canonical payload/signature
  - verification: public `IsCanonicalValid()`
  - canonical units: schema, proof signature, spec signature, prefix count and
    exact ordered prefix, session, StageClear ID/signature, sequence, stage, mode
- `C1CampaignDirectLootGrantBundle.v2`
  - preserves existing public grant fields and adds `admissionLineage`
  - explicit completion-aware verification: public `IsCanonicalValidV2()`
  - canonical units: schema, admission-lineage signature, ordinal, authoritative
    grant identity, selected base Item, StageClear/DropRequest/DropRollResult/
    RewardResult/claim/dedupe signatures, Item instance and entitlement signatures
  - legacy `C1CampaignDirectLootGrantBundle.v1` is not accepted as
    completion-aware proof
- `C1CampaignDirectLootSessionSnapshot.v2` continues to sign its specification,
  proof, effective completion prefix, recent-2 and accepted opportunities. Its
  validation replays every opportunity and requires each grant's pre-op prefix
  and spec to match the Reward-owned session history.

## 11. Failure / Edge Cases

- Null proof: reject session creation; empty completed-stage set: valid.
- Wrong authority/context/chapter, duplicate/unknown/gapped/reordered/malformed
  proof: reject before session creation.
- Ahead-of-gap first clear: reject before grant construction.
- Proof/spec/prefix/lineage/stage/mode/correlation tamper: public v2 verification
  false and containing session rejected atomically.
- Same StageClear ID with different bytes or same sequence with different fact:
  reject atomically.
- Byte-identical accepted StageClear retry: same snapshot and original grant.
- Session recreation: completion proof only; no accepted opportunity or recent
  history restored.

## 14. Downstream Consumption Order

### Mainline

1. Read authoritative completed stage IDs from the progression/save owner.
2. Pass the exact ordered chapter-1 prefix to
   `C1CampaignCompletionOnlyProgressProof.Create(...)` without adding Reward
   mode, roll, ordinal or Item data.
3. Call the completion-aware Reward `CreateSession` overload once for the new
   in-memory Reward session.
4. Submit real StageClear facts in Reward session-local sequence order.
5. Receive `C1CampaignDirectLootGrantBundle.v2` and transfer that exact object/
   canonical bytes downstream without rebuilding lineage or acquisition mode.

### Item entitlement acceptance

1. Require `C1CampaignDirectLootGrantBundle.v2` and non-null
   `C1CampaignDirectLootGrantAdmissionLineage.v1`.
2. Call `grant.IsCanonicalValidV2()` before any inventory, roster, placement,
   entitlement-history or dedupe mutation.
3. Read proof/spec/pre-op prefix/stage/mode from `admissionLineage`; never infer
   FirstClear/Repeat from ordinal, clearSequence or local completion state.
4. Correlate the active session token and accepted StageClear with the signed
   lineage, then consume the existing Reward-owned item materialization,
   claim/dedupe and entitlement exactly once.
5. Reject legacy v1, mismatch or tamper atomically. Do not reroll, recreate Item
   identity, rebuild Reward truth or persist Reward session/recent history.

The existing Item acceptance implementation is outside this package and must be
updated by its owner to consume the v2 verification path before Mainline mounts
the combined player-visible route.
